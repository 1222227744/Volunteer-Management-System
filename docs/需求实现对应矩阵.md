# 需求实现对应矩阵

本文用于将《软件需求规格说明书_2026-v1.2 / v1.3》中的功能需求、当前代码实现以及《系统设计说明书.md》中的设计分层进行一一对应，便于课程验收、代码走查与后续维护。
本文默认以“当前仓库已实现”为主，涉及尚未落地但在设计文档中保留的能力时，会明确标注为“课程版简化实现”或“后续扩展”。  
同时，本文参考 `概要设计v1`、`接口文档.md`、第三次迭代范围和第四次迭代范围，对 v3/v4 已完成事项和剩余边界做同步标注，避免旧文档与最新源文档脱节。

## 1. 对应原则

- 需求编号以 `SRS 4.2` 中的 `FR-01 ~ FR-08` 为准。
- 设计依据以《系统设计说明书》中的“展示层、接口层、领域层、基础设施层”划分为准。
- 代码对应优先列出“主要入口文件”，避免把一个功能拆成过细的文件清单。
- 若当前实现属于课程版简化实现，会在“说明”列中明确写出。

## 4. 演示数据覆盖情况

启动配置 `vms.demo-data.enabled=true` 时，系统会自动导入以下可展示数据。v3 默认关闭演示数据，避免生产环境误导入样例数据：

- 默认管理员、组织方和多名志愿者账号。
- 已结束、待开展的多场活动。
- 待审核、已通过、已驳回、已完成、已取消的报名数据。
- 已签到签退并沉淀的服务记录。
- 已提交的活动评价数据与评价概览。
- 审核通过、待审核、已驳回的投稿内容。
- 公告、用户级通知和反馈处理回执通知。
- 多笔捐赠记录。
- 公益资源、帮扶需求、资源匹配和荣誉激励记录。
- 已处理与待处理的反馈记录。
- 多条审计日志。

## 5. 当前与最新文档的差异说明

- `FR-02` 中复杂报名资格规则尚未形成独立规则引擎，目前通过参与要求、服务意向和人工审核承接。
- `FR-07` 的支付回调已通过 `DonationPaymentGateway` 保留网关边界，当前仍采用模拟网关；真实支付网关和回执下载仍作为后续扩展。
- `FR-08` 的申诉场景当前并入统一反馈处理流程，没有单独拆分申诉模块。
- 当前系统已使用 JWT，但未接入 Redis 或数据库持久会话。
- 邮件/短信已形成异步任务、失败记录和重试闭环，并通过 `ExternalNotificationSender` 保留发送适配端口。邮件通道可配置真实 SMTP 发送；短信通道仍为模拟实现。
- 文件上传已支持本地存储、类型/大小校验和文件审计，并通过 `FileObjectStorage` 保留对象存储替换点，第三方对象存储仍作为后续扩展。
- 数据库迁移治理已从纯运行时补丁演进为“`init.sql` + 版本化 SQL + 启动兼容判定”的轻量方案。v4 已评估 Flyway/Liquibase 替换路径，但为避免课程已有库 baseline 风险，本轮不强切标准框架。

## 6. 当前实现待收口项

以下问题仍应视为后续迭代待办或当前工程边界，而不是已经完全生产化的能力：

- 复杂报名资格规则尚未建模为独立规则引擎。
- 服务记录更正审批已在 v4 落地，后续可继续补充更细粒度的附件访问策略和批量审核能力。
- 审计覆盖已明显改善，但更多横切操作仍可继续补齐，例如通知手工发布、更多后台治理动作等。
- 自动化测试刚开始建立，覆盖面仍不足，尤其缺少更完整的数据层和前端交互回归测试。
- 数据库迁移目前仍是仓库内轻量实现，后续若继续演进，建议切换为标准迁移框架。
- 真实 SMTP 邮件已可配置接入；真实短信、真实支付和对象存储尚未接入。
