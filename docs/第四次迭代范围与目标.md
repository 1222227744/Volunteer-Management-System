# 第四次迭代范围与目标

本文档用于承接 v3 已完成后的剩余工程化缺口。第四次迭代不再扩大需求边界，重点围绕“生产化、可维护性、数据纠错和回归验证”推进，使系统从可演示的 v3 版本继续向更稳定的 v4 版本演进。

## 1. 当前基线

当前 `v4` 分支以 `v3` 完成状态为开发基线。系统已经具备注册登录、权限控制、活动管理、报名审核、签到签退、服务记录、内容审核、通知、资源对接、捐赠订单、文件上传、荣誉激励、统计审计和运维治理等核心功能。

与最新需求文档、概要设计文档和实现矩阵相比，v4 启动前存在以下需要继续收口的问题：

- 服务记录登记后缺少独立的更正申请、审核和修正闭环。
- 审计覆盖仍可继续扩大到更多后台治理和业务纠错动作。
- 自动化测试覆盖面不足，尚不能稳定覆盖支付回调、通知、权限、迁移兼容和关键状态流转。
- 外部邮件、短信、支付、对象存储仍以课程版模拟或本地实现为主，缺少清晰的适配边界。
- 数据库迁移仍采用仓库内轻量迁移器，尚未切换到标准 Flyway 或 Liquibase 方案。

## 2. v4 总目标

第四次迭代目标是提升系统的可纠错性、可验证性和工程边界清晰度。

v4 不以新增大模块为目标，而是优先完成以下方向：

1. 补齐服务记录更正申请、审核、驳回、应用更正和审计留痕。
2. 扩大关键业务动作的自动化测试覆盖。
3. 对外部通知、支付和文件存储建立更清晰的服务适配边界。
4. 继续强化生产部署和安全配置说明。
5. 评估轻量数据库迁移器向标准迁移框架演进的路径，降低长期维护风险。

## 3. 本轮优先开发范围

### 3.1 服务记录更正闭环

本轮首先实现服务记录更正闭环，范围如下：

- 志愿者可对自己的服务记录提交更正申请。
- 组织方只能处理自己发布活动所产生的服务记录更正申请。
- 管理员可处理全部服务记录更正申请。
- 更正申请需记录原服务时长、原服务成果、原证明材料、新服务时长、新服务成果、新证明材料、申请原因、申请人和申请时间。
- 审核通过后，系统应更新原服务记录，并按服务时长差额调整志愿者积分。
- 审核驳回后，系统应保留驳回原因，不修改原服务记录和积分。
- 更正申请、审核通过、审核驳回均应生成审计日志。
- 审核结果应通过站内通知告知申请人。

完成状态：已完成。系统已支持志愿者提交服务记录更正申请，组织方或管理员审核处理，审核通过后更新服务记录并按服务时长差额调整积分，审核驳回后保留原因且不修改原记录。

### 3.2 自动化测试补强

围绕 v3 和 v4 已实现的关键闭环补齐测试：

- 服务记录更正申请权限和状态流转测试。
- 支付回调 token 校验和订单状态流转测试。
- 活动状态变更、报名取消、签到签退异常更正测试。
- 通知已读、外部通知失败重试测试。
- 关键接口的角色权限边界测试。

完成状态：已完成本轮高优先级测试补强。当前已覆盖服务记录更正主流程、支付回调 token 校验、支付成功落库、外部通知失败重试、活动状态变更、通知已读等关键场景。前端交互自动化测试仍作为后续扩展。

### 3.3 外部服务适配边界

在不强制接入真实第三方平台的前提下，整理外部服务边界：

- 邮件/SMS 发送从控制器或业务服务中解耦为通道接口。
- 支付回调继续保留模拟能力，但明确网关接口、模拟实现和后续真实实现的替换点。
- 文件存储保留本地实现，同时抽象存储服务接口，便于后续替换为对象存储。

完成状态：已完成。外部通知发送已抽象为 `ExternalNotificationSender`，支付回调 token 生成和校验已抽象为 `DonationPaymentGateway`，文件物理存储已抽象为 `FileObjectStorage`。当前默认实现分别为模拟邮件/SMS、模拟支付网关和本地磁盘存储。

### 3.4 部署与安全配置

继续补齐部署层配置和说明：

- 明确生产 CORS 白名单配置。
- 补充 Nginx HTTPS、安全响应头和 WebSocket 反向代理说明。
- 补充后端服务守护进程示例配置。
- 保持演示数据和默认账号在生产默认关闭。

完成状态：已完成。系统已提供生产 CORS 白名单配置、API 安全响应头过滤器、Nginx HTTPS/HSTS/WebSocket 反向代理示例和 systemd 服务示例。演示数据和默认账号默认保持关闭。

### 3.5 数据库迁移框架评估

本轮完成标准迁移框架替换评估，结论如下：

- 当前项目已有 `init.sql`、版本化 SQL 脚本和 `schema_migrations` 历史表，能够支撑课程演示和已有库兼容升级。
- 直接切换 Flyway 或 Liquibase 需要为已存在数据库制定 baseline，若处理不当可能造成历史迁移重复执行或结构冲突。
- v4 本轮不强行替换迁移框架，继续保留轻量迁移器；若项目进入长期维护阶段，再以独立迭代完成 Flyway/Liquibase baseline、脚本命名和启动配置迁移。

完成状态：已完成评估，保留当前轻量迁移治理方案。

## 4. 暂不纳入本轮的内容

以下内容保留为后续扩展，不作为 v4 必须完成项：

- 真实短信服务商接入。
- 真实邮件 SMTP 账号联调。
- 真实支付网关商户号、签名和回调验签联调。
- 第三方对象存储账号联调。
- Redis 或数据库持久会话体系。
- 独立支持者/捐赠者角色体系。

## 5. v4 验收标准

v4 完成后，至少应满足以下标准：

- 服务记录更正流程可由志愿者发起，并由组织方或管理员完成审核处理。
- 服务记录更正通过后，服务时长、服务成果、证明材料和志愿者积分保持一致。
- 服务记录更正驳回后，原服务记录不被修改。
- 服务记录更正相关操作具备审计日志和通知反馈。
- 后端单元测试覆盖新增服务记录更正主流程。
- 前端服务记录页面能够展示更正申请、审核状态和处理入口。
- README 和需求实现矩阵能够反映 v4 已完成与仍保留扩展的边界。

## 6. v4 完成情况

当前 v4 范围已完成：

- 服务记录更正闭环已实现并具备审计和通知反馈。
- 外部通知、支付和文件存储已建立适配端口，默认保留课程版模拟或本地实现。
- 后端已补充服务记录更正、支付回调、外部通知失败重试等高价值单元测试。
- 部署配置已补充 API 安全响应头、Nginx HTTPS/WebSocket 示例和 systemd 服务示例。
- 数据库迁移框架已完成评估，当前不强切 Flyway/Liquibase，保留轻量迁移器作为课程版稳定方案。
