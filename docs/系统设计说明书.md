# 志愿者服务管理系统系统设计说明书

## 1. 文档目标

本说明书用于描述志愿者服务管理系统在选定技术栈下的系统设计方案，重点说明：

- 系统整体结构如何组织
- 各层职责如何划分
- 为什么采用这样的分层设计
- 各业务模块如何映射到当前仓库
- 该设计如何支撑 `SRS` 中的功能需求和非功能需求

本设计以当前项目已经落地的技术栈为前提，即前端采用 `Vue 3 + Vite`，后端采用 `Java 17 + Spring Boot 3.2 + Spring Data JPA`，数据库采用 `MySQL 8`，部署上采用前后端分离和 Nginx 反向代理。

本说明书属于归档性系统设计说明，保留架构分析、分层解释和演进判断；当前可运行版本、接口边界和部署方式请以 `README.md`、`docs/接口文档.md`、`docs/需求实现对应矩阵.md` 和 `docs/运维部署手册.md` 为准。

## 2. 设计目标

系统设计需要同时满足以下目标：

- 支撑用户、活动、报名、签到、服务记录、评价、审核、通知、反馈、捐赠、统计和审计等完整业务链。
- 保证关键流程的事务一致性和可追溯性。
- 适合课程项目小组按模块分工开发。
- 与当前仓库保持连续演进，而不是推翻重做。
- 为后续扩展短信、支付、对象存储和统一认证预留接口；邮件通道已通过适配器支持真实 SMTP。

## 3. 系统设计原则

本系统遵循以下设计原则：

- `高内聚、低耦合`：每个模块只负责一类清晰业务。
- `单体内模块化`：首版不拆微服务，但内部必须具备清晰边界。
- `分层解耦`：接口、业务、规则、数据访问分开组织。
- `事务优先`：报名、签到、服务记录、审核等关键流程保证一致性。
- `留痕优先`：关键状态变更必须审计可追踪。
- `可扩展`：外部接口通过适配器方式接入。
- `可演进`：优先复用当前代码结构，逐步增强。

## 4. 系统总体结构

### 4.1 总体视图

```text
用户浏览器
   |
Vue 3 前端
   |
Nginx
   |
Spring Boot REST API
   |
业务模块化单体
   |
分层架构
   |
MySQL / 文件存储 / 异步任务
```

### 4.2 为什么采用这样的总体结构

采用该结构的原因如下：

- `B/S` 架构与 SRS 要求一致，用户只需要浏览器即可访问。
- 前后端分离便于小组成员并行开发。
- 单体部署更适合课程项目环境，联调和演示成本低。
- REST API 简单清晰，便于文档编写和接口测试。
- MySQL 适合强事务业务，Redis 适合缓存和短期状态管理。

## 5. 分层架构设计

`概要设计v1` 从交付视角采用五层结构：

1. 展现层
2. 接口控制层
3. 业务服务层
4. 数据访问层
5. 数据库层

为了更清晰地映射当前仓库和后续重构方向，本文在逻辑上将其中的“业务服务层”继续细分为三部分，因此形成六层表达：

1. 展示层
2. 接口层
3. 应用层
4. 领域层
5. 基础设施层
6. 数据层

两种写法并不冲突：

- 五层结构更适合概要设计和答辩展示。
- 六层结构更适合解释当前仓库如何从 `Controller` 主导逐步演进到更清晰的业务分层。
- 当前仓库前两层与最后一层已经比较清晰，中间三层已在 v3/v4 中补充了通知、文件、支付、运维和服务记录更正等适配边界，后续仍可继续下沉控制器中的业务编排逻辑。

## 6. 展示层设计

### 6.1 展示层定义

展示层即前端 Web 应用，负责：

- 页面展示
- 交互流程控制
- 输入校验的前置提示
- 权限菜单和路由控制
- 图表展示和结果反馈

当前仓库对应内容主要包括：

- [frontend/src/router/index.js](../frontend/src/router/index.js)
- [frontend/src/stores/auth.js](../frontend/src/stores/auth.js)
- `frontend/src/views/` 下各业务页面

### 6.2 为什么前端单独作为展示层

这样设计的原因如下：

- 符合前后端分离架构，前端只负责交互，不承担核心业务规则。
- 便于页面、接口、后端逻辑分开开发。
- 有利于同时支持 PC 和移动浏览器。
- 当前仓库已具备清晰的前端页面与路由结构，后续可按需逐步补充类型约束。

### 6.3 展示层的设计重点

- 当前使用 `Vue Router` 做页面路由管理和角色限制。
- 当前使用轻量本地状态管理登录态和用户信息。
- 当前页面使用原生表单与基础样式实现交互。
- 统计页面当前以基础看板展示为主，后续可按需引入图表能力。
- 所有业务数据从后端 API 获取，不在前端固化规则。

### 6.4 为什么不把业务规则放在前端

因为前端不可信，也不适合承担核心规则判断。比如：

- 报名名额是否已满
- 用户是否具备审核权限
- 签退是否有效
- 服务时长如何计算

这些规则必须由后端统一控制，否则会造成权限绕过和数据不一致。

## 7. 接口层设计

### 7.1 接口层定义

接口层对应后端的 `Controller/API`，负责：

- 接收 HTTP 请求
- 参数接收与格式校验
- 调用应用层服务
- 统一响应格式
- 向前端暴露 RESTful API

当前仓库中典型接口层文件包括：

- [backend/src/main/java/com/volunteer/vms/auth/AuthController.java](../backend/src/main/java/com/volunteer/vms/auth/AuthController.java)
- [backend/src/main/java/com/volunteer/vms/activity/ActivityController.java](../backend/src/main/java/com/volunteer/vms/activity/ActivityController.java)
- [backend/src/main/java/com/volunteer/vms/dashboard/DashboardController.java](../backend/src/main/java/com/volunteer/vms/dashboard/DashboardController.java)

### 7.2 为什么单独设接口层

原因如下：

- 将 HTTP 协议细节与业务逻辑分离。
- 便于统一参数校验、错误处理和返回结构。
- 降低前端接口变更对内部业务实现的影响。
- 适合后续扩展为 OpenAPI 文档或第三方接口。

### 7.3 接口层应该做什么

- 接收 DTO 或请求体
- 做基础参数校验
- 获取当前登录用户
- 调用应用层服务
- 返回统一 `ApiResponse`

### 7.4 接口层不应该做什么

- 不承担复杂业务流程编排
- 不直接写大量数据库查询逻辑
- 不计算复杂业务规则
- 不混入统计口径和审计策略细节

### 7.5 为什么要控制接口层的职责

如果把业务规则堆在 Controller 中，会出现以下问题：

- 代码难以复用
- 事务边界不清晰
- 单元测试困难
- 控制器臃肿，不利于多人协作

当前仓库里的 `ActivityController` 已经包含一定业务处理逻辑，后续建议逐步下沉到应用层和领域层。

## 8. 应用层设计

### 8.1 应用层定义

应用层对应 `Application Service`，负责：

- 编排完整业务用例
- 控制事务边界
- 组织多个模块之间的调用
- 触发通知、审计和异步任务
- 协调领域对象与基础设施对象

典型业务用例包括：

- 用户注册与登录
- 创建活动
- 活动报名
- 报名审核
- 签到签退
- 活动取消并通知相关人员
- 服务记录生成
- 反馈处理与回执返回

### 8.2 为什么必须有应用层

应用层是本项目设计里最关键的一层，原因如下：

- 你们的业务不是简单 CRUD，而是完整流程型业务。
- 很多流程跨多个实体，例如活动、报名、通知、日志。
- 事务边界必须在业务用例级别定义，而不是写散在控制器里。
- 后续继续增强异步通知、导出任务和外部接口时，应用层仍是最合适的编排位置。

### 8.3 应用层要解决的典型问题

例如“活动取消”这个场景，并不是简单改一个状态，而是：

1. 检查操作者权限
2. 更新活动状态
3. 更新相关报名状态
4. 记录审计日志
5. 生成通知
6. 触发异步发送

这些步骤属于一个完整业务用例，最适合由应用层统一编排。

### 8.4 为什么不把这些逻辑留在 Controller 或 Repository

- 放在 Controller，会导致接口层过重。
- 放在 Repository，会把数据访问层变成业务层，破坏分层。
- 放在应用层，可以形成清晰的事务和流程边界。

## 9. 领域层设计

### 9.1 领域层定义

领域层负责表达系统中最核心、最稳定的业务规则，包括：

- 活动状态流转规则
- 报名资格与名额规则
- 签到签退规则
- 服务时长计算规则
- 评价与排行规则
- 内容审核状态规则

### 9.2 为什么这个项目需要领域层

虽然这是课程项目，但并不是只有增删改查。SRS 已经写明了很多规则，例如：

- 报名截止时间不得晚于活动开始时间
- 活动满员后不允许继续报名
- 只有审核通过的用户才能签到
- 签退时间不得早于签到时间
- 服务时长需要按规则核算
- 只有有正式服务记录的用户才能评价

这些规则不属于界面，也不属于数据库，它们属于业务本身，因此应该放在领域层。

### 9.3 领域层为什么采用 DDD-lite

这里采用 `DDD-lite`，而不是完整重型领域驱动设计，原因如下：

- 课程项目不需要引入过多抽象概念。
- 业务规则已经足够多，仍然需要单独沉淀。
- 只保留最有价值的部分：实体、状态、规则、领域服务。
- 这样既能提升设计质量，又不会过度复杂化。

### 9.4 领域层的典型内容

- `ActivityStatus`
- `RegistrationStatus`
- `ContentStatus`
- `FeedbackStatus`
- 服务时长计算规则
- 报名占位规则
- 排行计算规则

### 9.5 为什么状态枚举很重要

你们系统是典型的状态驱动系统：

- 活动有状态
- 报名有状态
- 内容有状态
- 反馈有状态
- 捐赠有状态

明确的状态枚举有三个作用：

- 保证流程一致性
- 便于前后端统一展示
- 便于统计、筛选和审计

## 10. 基础设施层设计

### 10.1 基础设施层定义

基础设施层负责技术实现细节，包括：

- 数据库存取
- 缓存访问
- 文件存储
- 身份令牌处理
- 异步任务执行
- 外部服务适配
- 审计日志持久化

当前仓库中可归入基础设施支撑能力的内容包括：

- [backend/src/main/java/com/volunteer/vms/auth/TokenSessionService.java](../backend/src/main/java/com/volunteer/vms/auth/TokenSessionService.java)
- [backend/src/main/java/com/volunteer/vms/audit/AuditLogService.java](../backend/src/main/java/com/volunteer/vms/audit/AuditLogService.java)
- `Repository` 接口族

### 10.2 为什么必须单独划分基础设施层

原因如下：

- 外部技术实现不应该污染核心业务规则。
- 未来如果从本地文件切换到对象存储，不应影响业务模块。
- 未来如果从当前签名 JWT 加内存撤销表切到 Redis 持久化撤销，不应影响业务用例层。
- 未来接入真实短信、真实支付和第三方对象存储时，应只替换适配器实现。

### 10.3 基础设施层的具体设计选择

#### 10.3.1 数据库访问

当前采用 `Spring Data JPA`。

原因：

- 与现有工程一致
- 简化基础 CRUD
- 提升首版开发效率

对于复杂统计查询，后续使用原生 SQL 或补充 MyBatis。

#### 10.3.2 鉴权与会话

当前仓库通过 `TokenSessionService` 生成 HMAC-SHA256 签名 JWT，令牌中包含用户、角色、签发时间、过期时间和 `jti`。用户登出时，系统将 `jti` 写入内存撤销表，用于在令牌过期前阻止继续使用。

这是一个适合当前演示版本的轻量实现，已经具备 Bearer Token 鉴权、过期时间校验和登出失效能力；若继续生产化，建议升级为：

- 将 JWT 撤销表或会话黑名单持久化到 `Redis`
- 保留统一令牌解析接口
- 增加刷新令牌、强制下线和多端登录治理

这样设计的原因是：

- 当前内存撤销表在后端重启后会丢失，已登出的令牌在未过期前可能重新可用。
- Redis 更适合实现锁定策略、过期控制和扩展登录能力。

#### 10.3.3 审计日志

`AuditLogService` 单独存在是正确的方向。

这样设计的原因是：

- 审计是跨模块横切能力
- 活动、审核、签到、账号管理都要调用
- 集中处理更容易统一日志格式和查询口径

#### 10.3.4 文件存储

当前仓库已落地通用文件上传下载链路，主要由 `FileController`、`FileStorageService`、`FileObjectStorage`、`LocalFileObjectStorage` 和 `file_assets` 表组成。

当前设计选择为本地文件存储，上传时记录文件分类、原始文件名、存储文件名、大小、上传人、客户端 IP 和业务关联对象，并对图片、附件的后缀和真实文件头做基础校验。

这样设计的原因是：

- 课程项目部署简单，不依赖额外对象存储服务
- 能满足活动附件、成果图片和证明材料等基础场景
- 已通过 `FileObjectStorage` 保留替换点，后续可切换为 `MinIO`、阿里云 OSS 或腾讯云 COS

#### 10.3.5 异步任务

当前仓库已落地站内通知、WebSocket 推送、外部通知任务和 CSV 导出能力。站内通知先写入 `notifications` 表，再尝试通过 WebSocket 推送；外部邮件/短信任务写入 `external_notification_tasks` 表，并由 `ExternalNotificationService` 通过 `@Async` 异步发送和重试。

统计导出和审计导出当前采用同步 CSV 下载方式，适合课程验收和小规模数据量；若后续出现大批量导出或定时任务需求，可继续引入 `Spring Scheduling`、任务队列表或消息队列。

这样设计的原因是：

- 通知发送失败不影响主业务事务提交
- 外部发送结果可查询、可重试、可审计
- 同步 CSV 导出实现简单，已能满足当前验收场景

## 11. 数据层设计

### 11.1 数据层定义

数据层即持久化存储层，主要包括：

- 业务主数据库 `MySQL`
- 可选缓存层 `Redis`

### 11.2 为什么主业务数据使用 MySQL

因为本系统核心是事务型业务系统，MySQL 适合：

- 活动、报名、服务记录等结构化数据
- 多表关联和状态管理
- 事务一致性控制
- 索引优化和分页查询

### 11.3 数据表设计思想

根据当前 `init.sql`，表结构围绕以下核心实体展开：

- `users`
- `activities`
- `activity_registrations`
- `activity_attendance_corrections`
- `service_records`
- `service_record_corrections`
- `activity_feedbacks`
- `content_posts`
- `announcements`
- `donations`
- `donation_orders`
- `feedbacks`
- `public_resources`
- `help_needs`
- `resource_matches`
- `file_assets`
- `honor_records`
- `notifications`
- `external_notification_tasks`
- `system_configs`
- `incident_records`
- `audit_logs`

此外，启动迁移器会维护 `schema_migrations` 历史表，用于记录仓库内版本化 SQL 脚本的执行情况。

这样设计的原因是：

- 能直接对应 SRS 中的功能模块
- 结构清晰，适合课程项目 ER 图与数据库说明
- 便于后续做统计报表和日志追踪

### 11.4 数据层需要重点关注的设计

- 对活动、报名、服务记录、日志等高频查询表建立必要索引
- 所有关键业务表使用明确状态字段
- 时间字段统一命名，便于统计与排序
- 保证唯一约束，例如同一用户同一活动只能有一条有效报名

### 12.2 为什么按业务模块拆包

原因如下：

- 比单纯按技术层拆包更容易对应业务需求。
- 更适合小组成员按模块认领任务。
- 便于答辩时说明“系统围绕业务域组织”。

### 12.3 建议的进一步优化

后续可在每个业务模块内部进一步形成：

- `controller`
- `application`
- `domain`
- `repository`
- `dto`

这样能让“模块化单体 + 分层”更加彻底。

## 13. 非功能需求支撑设计

### 13.1 性能

为了满足当前 v4 的性能与可维护性目标，系统已经采用以下设计：

- MySQL 表结构补充必要索引和唯一约束
- 统计和审计导出使用后端查询结果生成 CSV
- 列表接口优先采用分页、筛选和排序，避免前端全量处理
- 外部通知发送异步化，避免邮件或短信通道阻塞主业务事务

### 13.2 安全

为了满足安全需求，设计上采用：

- 统一鉴权
- RBAC 角色授权
- 密码加密存储
- 高风险操作审计
- 敏感信息最小化暴露

### 13.3 可维护性

为了满足可维护性，设计上采用：

- 模块化拆分
- 分层隔离
- DTO 与实体分离
- 统一响应和异常处理

### 13.4 可扩展性

为了满足扩展性，设计上采用：

- 外部能力用适配器接口封装
- 异步能力使用轻量事件机制
- 数据访问保留从 JPA 扩展到 MyBatis 的空间
- 缓存和文件存储均可平滑替换实现

## 14. 最终设计结论

本系统最终设计选择是：

- 前端作为独立展示层，负责页面交互和权限路由控制
- 后端采用模块化单体，并按接口层、应用层、领域层、基础设施层分层组织
- MySQL 负责核心事务数据；若后续引入 Redis，则负责缓存和短期状态
- 轻量异步机制负责通知、提醒和导出等非核心同步流程
- 审计日志作为横切能力统一治理

这样设计的根本原因是：

- 它最符合你们的 `SRS`
- 它与当前仓库最连续
- 它最适合课程项目稳定交付
- 它在不过度复杂化的前提下，已经具备较成熟的信息系统架构特征

## 15. 历史迭代收口说明

第二次迭代不改变总体架构，重点曾放在以下三类收口工作：

- 业务闭环补齐：活动状态流转、活动取消联动通知、基础活动评价、服务记录重复防护与更正留痕。
- 治理能力收口：广播通知改为用户级已读、审计日志真实分页导出、关键操作审计补齐。
- 数据一致性增强：组织方数据权限收紧、数据库约束与索引补齐、迁移方案替代临时修补。

上述内容已在后续 v3/v4 中继续扩展：当前系统已经具备 JWT 登录态、文件上传审计、WebSocket 站内通知、外部通知任务、支付确认闭环、资源对接、荣誉激励、运维治理和服务记录更正闭环。

当前交付口径为：

- 演示与验收使用 `backend/src/main/resources/sql/demo-data.sql` 和 `backend/api-demo.http`。
- 后端按交付要求不保留 `backend/src/test` 自动化测试目录；若进入长期维护阶段，应重新补齐自动化回归测试。
- 数据库迁移治理继续采用 `init.sql`、`sql/migrations/` 和启动兼容判定；若长期维护，再以独立迭代切换 Flyway 或 Liquibase。

历史范围见 [第二次迭代范围与目标.md](./第二次迭代范围与目标.md)、[第三次迭代范围与目标.md](./第三次迭代范围与目标.md) 和 [第四次迭代范围与目标.md](./第四次迭代范围与目标.md)。
