# 第三次迭代范围与目标

本文档用于承接《软件需求规格说明书_2026-v1.2》中 3.2 产品功能、4.1 功能概述表以及新增《接口文档.md》中已经提出但当前项目尚未完整落地的能力。第三次迭代不再只做文档对齐，而是以补齐缺口为目标，推动系统从课程版 v2 向更完整的 v3 演进。

## 1. 当前基线

当前 `main` 分支已经完成 v2 的核心业务闭环，包括活动发布、报名审核、签到签退、服务记录、活动评价、通知、审计、统计看板、演示数据和轻量数据库迁移治理。

但与最新需求和接口文档相比，仍存在以下问题：

- 需求文档中写到的若干业务模块仍是简化实现或尚未实现。
- 接口文档中出现了第三方通知、支付回调、文件上传、WebSocket、JWT、部署与通信接口等能力，当前项目尚未完整支撑。
- 当前系统仍保留演示数据默认启用、内存 token、轻量迁移、模拟捐赠等课程版特征。

## 2. v3 总目标

第三次迭代目标是补齐最新文档中已经明确出现、但当前系统尚未完整实现的功能能力和接口能力。

v3 重点不是重写系统，而是在现有 Spring Boot + Vue 架构基础上补齐以下方向：

1. 用户资料、账号状态与权限治理。
2. 活动编辑、筛选、报名撤销和更细活动规则。
3. 签到签退异常更正与服务档案完善。
4. 评价激励、优秀志愿者和风采展示能力。
5. 公益资源对接和资源流转管理。
6. 文件上传、附件管理和文件审计。
7. 通知通信增强，包括站内通知实时推送和外部通知预留。
8. 捐赠支付从直接落库升级为可模拟回调的支付闭环。
9. 登录态、部署配置、接口规范和数据库治理进一步工程化。

## 3. 业务功能待补齐

### 3.1 用户权限管理

待完成：

- 用户个人资料维护：支持用户修改昵称、联系方式、服务意向等基础资料。
- 实名身份核验状态：至少在数据模型中保存核验状态，支持管理员审核或标记。
- 账号状态管理：支持启用、停用、锁定等账号状态，登录和业务操作必须受账号状态约束。
- 用户资质审核：支持管理员查看待审核用户并给出通过或不通过结果。
- 权限边界细化：继续收紧组织方、管理员、志愿者之间的数据访问范围。

### 3.2 志愿活动管理

待完成：

- 活动信息编辑：支持组织方和管理员修改已创建活动的标题、描述、地点、时间、人数和参与要求。
- 活动下架机制：区分活动取消、活动结束和活动下架，避免所有下线场景都混用取消状态。
- 活动筛选检索：支持按状态、时间、地点、关键词等条件筛选活动。
- 招募规则扩展：补充报名截止时间、志愿者服务意向或条件要求等基础规则。
- 活动附件：支持活动说明附件或宣传图片上传。

### 3.3 活动报名审核

待完成：

- 志愿者主动取消报名：允许志愿者在规则允许范围内撤销报名。
- 报名资格校验：报名时按活动招募规则校验是否满足参与条件。
- 报名审核说明：审核通过、驳回或取消时支持填写处理说明。
- 报名进度提醒：报名提交、审核完成、活动变更时形成更完整的通知链路。

### 3.4 服务考勤记录

待完成：

- 志愿者自主签到签退：支持志愿者在符合活动规则时自行完成签到或签退。
- 二维码签到能力：支持活动生成签到码，前端提供扫码或输入码完成签到。
- 人工签到备选流程：组织方或管理员可在无扫码条件下人工确认签到签退。
- 异常考勤更正：支持管理员或组织方对异常签到签退发起更正，并保留处理痕迹。
- 服务记录纠错：已生成服务记录出现错误时，支持更正申请、审核和审计留痕。
- 服务电子档案增强：按志愿者聚合活动、时长、评价、荣誉和证明材料。

### 3.5 评价激励管理

待完成：

- 优秀志愿者评定：基于服务时长、参与次数、评价结果等信息生成候选名单，并支持管理员确认。
- 荣誉和积分规则：将当前简单积分扩展为可配置规则，明确积分来源和发放条件。
- 风采展示：支持优秀志愿者事迹内容发布、审核和公开展示。
- 激励记录留存：保存积分、荣誉或表彰产生原因、关联活动和发放时间。

### 3.6 资讯公告通知

待完成：

- 资讯分类管理：区分公告、公益资讯、行业动态、风采展示等内容类型。
- 内容上下架：支持公开内容发布、下架和状态管理。
- 定向通知：支持按角色、活动参与人或指定用户发送通知。
- 通知已读统计：管理员或组织方可查看通知触达和已读情况。

### 3.7 公益资源对接

待完成：

- 公益资源登记：登记物资、资金等资源的来源、类别、数量、可用范围和状态。
- 帮扶需求登记：记录公益帮扶需求的对象、内容、数量、地点和时间要求。
- 资源需求匹配：建立资源与需求之间的匹配关系，并记录匹配状态。
- 项目进度跟进：记录资源从匹配、分配、使用到完成的推进过程。
- 资源流转审计：防止资源重复分配，保留资源去向和处理记录。

### 3.8 数据统计分析

待完成：

- 活动趋势统计：按时间维度统计活动数量、报名人数和完成情况。
- 用户活跃度统计：统计登录、报名、参与、反馈等用户活跃行为。
- 服务贡献分析：按志愿者、活动、组织方维度汇总服务时长和服务成果。
- 资源对接统计：统计资源登记、匹配、使用和完成情况。
- 数据导出：支持关键统计数据导出。

### 3.9 意见反馈与系统运维

待完成：

- 系统配置管理：提供基础配置项管理能力，例如演示数据开关、报名规则、通知配置等。
- 运行状态检查：提供基础健康检查接口或管理页展示。
- 操作审计扩展：继续补充关键业务动作的审计覆盖。
- 故障处理记录：支持管理员记录系统问题、处理措施和处理结果。

## 4. 接口文档能力待补齐

### 4.1 前后端通信接口

待完成：

- 将前端 HTTP 客户端从当前原生 `fetch` 封装升级为接口文档所述的 Axios 统一客户端，或调整接口文档统一描述为当前封装；若以接口文档为准，则 v3 应引入 Axios。
- 统一请求拦截器和响应拦截器，处理鉴权令牌注入、401、403、500 等错误场景。
- 将当前内存 token 登录态升级为 JWT，或实现等价的可持久、可校验 token 方案。
- 统一接口响应格式，明确成功响应、错误响应、文件响应三类结构。
- 梳理 REST 方法规范，补齐 `GET`、`POST`、`PATCH`、`PUT`、`DELETE` 的使用边界。

### 4.2 通知通信接口

待完成：

- WebSocket 站内实时通知：当系统生成新通知时，在线用户能够实时收到推送。
- 通知落库与推送一致性：站内通知仍以数据库为准，实时推送失败不能影响通知记录保存。
- 邮件通知接口：预留或实现 SMTP 发送能力，用于重要业务通知。
- 短信通知接口：预留或实现第三方 SMS API 调用能力，用于验证码或关键提醒。
- 异步通知处理：引入线程池、队列或其他异步机制，避免外部通知阻塞主业务流程。
- 通知失败重试与异常记录：外部通知失败时记录失败原因，并支持后续重试或人工处理。

### 4.3 支付与捐赠接口

待完成：

- 捐赠订单模型：从直接写入捐赠记录升级为先生成捐赠订单。
- 模拟支付控制台：演示环境支持模拟支付成功、失败、取消等状态。
- 支付结果回调接口：提供回调入口，接收支付平台或模拟支付模块返回的支付结果。
- 回调安全校验：对回调参数进行签名校验或等价防伪校验。
- 支付状态流转：明确待支付、支付成功、支付失败、已关闭等状态。
- 捐赠记录生成：仅在支付成功后生成正式捐赠记录或将订单转为已完成捐赠。

### 4.4 文件传输接口

待完成：

- 通用文件上传接口：支持 `multipart/form-data` 上传。
- 活动附件上传：支持活动相关附件或图片上传。
- 内容投稿图片上传：支持资讯、风采或内容投稿上传图片。
- 服务证明材料上传：替代当前仅保存 `evidenceUrl` 文本链接的简化方案。
- 文件类型和大小限制：图片限制 jpg、jpeg、png、gif；附件限制 pdf、docx、xlsx、pptx、zip、rar。
- 文件真实类型校验：不能只依赖后缀名，需要校验 MIME 类型或文件签名。
- 文件审计表：保存文件原始名称、存储名称、大小、上传人、上传时间、客户端 IP 和业务关联对象。
- 文件访问权限：根据上传文件所属业务控制下载或查看权限。

### 4.5 通信与部署接口

待完成：

- HTTPS 部署方案：补充 Nginx HTTPS、证书和反向代理配置。
- HSTS 与安全响应头：生产环境支持基础安全头配置。
- systemd 服务管理：提供后端服务的 systemd 示例配置。
- 健康检查接口：提供部署层可调用的健康检查端点。
- 生产 CORS 策略：从当前宽松跨域配置收紧为明确允许的前端域名和方法。
- 性能目标验证：若文档继续保留 TPS 和响应时间指标，需要补充压测脚本或验收说明。

## 5. 数据库与迁移待补齐

待完成：

- 标准迁移框架：从当前轻量迁移机制升级为 Flyway 或 Liquibase。
- 生产环境禁用 `ddl-auto=update`：逐步调整为迁移脚本驱动结构变更。
- MySQL 字符集统一：明确使用 `utf8mb4` 并校验连接串和建表语句一致。
- 新增业务表：用户资料、账号审核、活动附件、报名审核说明、异常考勤更正、荣誉激励、公益资源、帮扶需求、资源匹配、支付订单、文件审计、系统配置等表。
- 索引补齐：围绕用户、活动、报名状态、通知、资源匹配、支付状态、文件业务关联等高频查询建立索引。
- 状态枚举规范：统一各模块状态字段的数据库表示和 Java 枚举映射。

## 6. 演示版残留待收口

待完成：

- 演示数据不应在生产环境默认启用。
- 默认管理员和组织方账号不应在生产环境默认创建。
- 内存 token 会话需要升级为 JWT、Redis 或数据库持久会话。
- 捐赠流程不能长期停留在直接落库模拟。
- 文件上传、外部通知、支付回调等接口需要明确当前实现和后续扩展边界。

## 7. 建议开发顺序

建议 v3 分为四个阶段推进：

1. 接口与基础设施阶段：JWT/Axios、CORS 收紧、健康检查、文件上传基础能力、数据库迁移框架。
2. 业务补齐阶段：用户资料与账号状态、活动编辑与筛选、报名撤销、异常考勤更正、服务档案。
3. 扩展模块阶段：公益资源对接、支付订单与模拟回调、优秀志愿者评定、风采展示。
4. 通信与治理阶段：WebSocket 通知、邮件/SMS 预留或实现、系统配置、审计扩展、统计增强。

## 8. v3 验收标准

v3 完成后，至少应满足以下标准：

- 《软件需求规格说明书_2026-v1.2》3.2 中九大模块均有对应的可运行功能或明确的后续扩展说明。
- 《接口文档.md》中写到的核心接口能力不再停留在文档描述，至少完成 JWT/Axios、文件上传、模拟支付回调、WebSocket 站内通知中的主要闭环。
- 系统不再依赖默认演示数据和默认账号作为正常运行前提。
- 数据库结构变更通过标准迁移脚本管理。
- 关键业务操作具备权限控制、状态校验、通知或审计留痕。
- 前端页面能够支撑新增核心流程的演示和基本测试。
