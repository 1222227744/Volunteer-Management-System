# 运维部署手册

本文档面向志愿者服务管理系统的本地验收、课程验收和小规模真实部署。内容以当前 `v4` 代码和仓库内脚本为准，覆盖环境准备、配置生成、数据库初始化、构建部署、日常运维、备份恢复、故障处理和安全注意事项。

## 1. 系统组成

系统采用前后端分离架构：

| 组件 | 技术 | 默认端口 | 说明 |
| --- | --- | --- | --- |
| 前端 | Vue 3 + Vite | `5173` 开发，`4173` 预览 | 生产环境构建为静态文件，由 Nginx 托管 |
| 后端 | Spring Boot 3.2 + Java 17 | `8080` | 提供 REST API、WebSocket、文件上传下载和外部通知适配 |
| 数据库 | MySQL 8 | `3306` | 保存用户、活动、报名、服务记录、通知、审计等业务数据 |
| 反向代理 | Nginx | `80` / `443` | 托管前端静态文件并反向代理 `/api/`、`/ws/` |
| 服务守护 | systemd | 无 | Linux 生产部署时守护后端 Jar 进程 |

## 4. 配置文件

### 4.1 后端配置

后端真实配置文件为 `backend/.env`，不应提交到 Git。模板文件为 `backend/.env.example`。

核心配置项：

| 配置项 | 示例 | 说明 |
| --- | --- | --- |
| `SERVER_ADDRESS` | `0.0.0.0` | 后端监听地址 |
| `SERVER_PORT` | `8080` | 后端端口 |
| `SPRING_DATASOURCE_URL` | `jdbc:mysql://127.0.0.1:3306/volunteer_service?...` | MySQL 连接串 |
| `SPRING_DATASOURCE_USERNAME` | `root` | 数据库用户名 |
| `SPRING_DATASOURCE_PASSWORD` | `your_password` | 数据库密码 |
| `SPRING_JPA_HIBERNATE_DDL_AUTO` | `none` | 当前项目使用 SQL 管理结构，保持 `none` |
| `VMS_BOOTSTRAP_ENABLED` | `false` | 是否启动时创建默认管理员和组织方账号 |
| `VMS_JWT_SECRET` | 随机 32 字节以上字符串 | JWT 签名密钥，生产环境必须修改 |
| `VMS_FILE_STORAGE_DIR` | `./uploads` | 上传文件目录 |
| `VMS_CORS_ALLOWED_ORIGIN_PATTERNS` | `https://volunteer.example.com` | 前端域名白名单 |
| `VMS_EMAIL_ENABLED` | `false` / `true` | 是否启用真实 SMTP 邮件 |
| `VMS_EMAIL_HOST` | `smtp.example.com` | SMTP 主机 |
| `VMS_EMAIL_PORT` | `465` / `587` | SMTP 端口 |
| `VMS_EMAIL_USERNAME` | 邮箱账号 | SMTP 登录账号 |
| `VMS_EMAIL_PASSWORD` | 授权码 | SMTP 授权码或密码 |
| `VMS_EMAIL_FROM` | 发件邮箱 | 邮件发件地址 |

安全要求：

- `backend/.env` 不允许提交。
- `VMS_JWT_SECRET` 不允许使用模板默认值。
- 真实邮箱授权码、数据库密码不得写入 README、接口文档或 SQL 脚本。
- 生产环境建议关闭 `VMS_BOOTSTRAP_ENABLED`，账号通过注册或后台流程创建。

### 4.2 前端配置

前端真实配置为 `frontend/.env`，模板为 `frontend/.env.example`。

| 配置项 | 示例 | 说明 |
| --- | --- | --- |
| `VITE_BACKEND_ORIGIN` | `http://127.0.0.1:8080` | 开发环境代理目标 |
| `VITE_DEV_HOST` | `0.0.0.0` | 前端开发服务监听地址 |
| `VITE_DEV_PORT` | `5173` | 前端开发端口 |
| `VITE_PREVIEW_HOST` | `0.0.0.0` | 前端预览监听地址 |
| `VITE_PREVIEW_PORT` | `4173` | 前端预览端口 |

生产环境使用 Nginx 托管静态文件时，前端不直接读取 `.env` 中的后端地址，浏览器访问同域 `/api/` 和 `/ws/`，由 Nginx 反向代理到后端。

## 5. 一键配置脚本

仓库提供两个脚本，用于基于相对路径创建 `.env` 文件、写入数据库连接、生成 JWT 密钥并创建上传目录。

### 5.1 Ubuntu

```bash
bash scripts/setup-ubuntu.sh --db-user root --db-password '你的MySQL密码'
```

可选参数：

| 参数 | 说明 |
| --- | --- |
| `--db-host` | 数据库地址，默认 `127.0.0.1` |
| `--db-port` | 数据库端口，默认 `3306` |
| `--db-name` | 数据库名，默认 `volunteer_service` |
| `--db-user` | 数据库用户，默认 `root` |
| `--db-password` | 数据库密码，不传则交互输入 |
| `--init-db` | 执行 `init.sql` 初始化结构 |
| `--with-demo` | 在 `--init-db` 后导入 `demo-data.sql` |

完整示例：

```bash
bash scripts/setup-ubuntu.sh \
  --db-host 127.0.0.1 \
  --db-port 3306 \
  --db-name volunteer_service \
  --db-user root \
  --db-password '你的MySQL密码' \
  --init-db \
  --with-demo
```

### 5.2 Windows

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup-windows.ps1 `
  -DbUser root `
  -DbPassword "你的MySQL密码"
```

完整示例：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup-windows.ps1 `
  -DbHost 127.0.0.1 `
  -DbPort 3306 `
  -DbName volunteer_service `
  -DbUser root `
  -DbPassword "你的MySQL密码" `
  -InitDb `
  -WithDemo
```

脚本执行后会生成或更新：

- `backend/.env`
- `frontend/.env`
- `backend/uploads/`

脚本不会提交任何真实配置。

## 6. 数据库运维

### 6.1 初始化结构

首次部署空库时执行：

```sql
SOURCE backend/src/main/resources/sql/init.sql;
```

说明：

- `init.sql` 会创建 `volunteer_service` 数据库并切换到该库。
- 字符集使用 `utf8mb4`。
- 表结构覆盖当前 v4 所需的主要表和索引。
- 运行时还有轻量迁移器读取 `sql/migrations/`，用于兼容已有库补字段、补索引。

### 6.2 导入样例数据

展示或接口冒烟测试需要样例数据时执行：

```sql
SOURCE backend/src/main/resources/sql/demo-data.sql;
```

样例账号：

| 角色 | 用户名 | 密码 |
| --- | --- | --- |
| 管理员 | `admin@example.com` | `admin123` |
| 组织方 | `organizer@example.com` | `organizer123` |
| 志愿者 | `liuqi@example.com` | `volunteer123` |
| 志愿者 | `chenmo@example.com` | `volunteer123` |
| 志愿者 | `linan@example.com` | `volunteer123` |

注意：

- `demo-data.sql` 只应用于展示、验收和本地测试。
- 正式生产库不要导入样例数据。
- 脚本会先清理自己创建的样例账号、样例活动、样例资源和关联数据，再重新插入，便于重复导入。
- 样例账号使用邮箱格式用户名，便于真实 SMTP 邮件发送验证。

### 6.3 备份

建议每日备份数据库，并在版本发布前额外备份一次。

```bash
mysqldump \
  --default-character-set=utf8mb4 \
  -h 127.0.0.1 \
  -P 3306 \
  -u root \
  -p \
  volunteer_service > backup-volunteer-service-$(date +%F-%H%M).sql
```

Windows PowerShell 示例：

```powershell
$ts = Get-Date -Format "yyyyMMdd-HHmm"
mysqldump --default-character-set=utf8mb4 -h 127.0.0.1 -P 3306 -u root -p volunteer_service > "backup-volunteer-service-$ts.sql"
```

备份策略建议：

- 最近 7 天保留每日备份。
- 最近 4 周保留每周备份。
- 发布前备份至少保留到下一次稳定版本。
- 备份文件不得放在 Web 静态目录下。

### 6.4 恢复

恢复前先确认目标库可以被覆盖，并停止后端服务。

```bash
sudo systemctl stop volunteer-service-backend
mysql -h 127.0.0.1 -P 3306 -u root -p volunteer_service < backup.sql
sudo systemctl start volunteer-service-backend
```

恢复后检查：

```sql
SELECT COUNT(*) FROM users;
SELECT COUNT(*) FROM activities;
SELECT COUNT(*) FROM audit_logs;
```

## 8. 构建与发布

### 8.1 后端构建

当前仓库按交付要求不保留 `backend/src/test` 自动化测试目录，构建命令为：

```bash
mvn -q -f backend/pom.xml -DskipTests package
```

产物：

```text
backend/target/volunteer-service-backend-0.0.1-SNAPSHOT.jar
```

### 8.2 前端构建

```bash
npm --prefix frontend install
npm --prefix frontend run build
```

产物：

```text
frontend/dist/
```

### 8.3 Linux 发布流程

示例以 `/opt/volunteer-service` 为部署目录。

```bash
sudo mkdir -p /opt/volunteer-service/backend/uploads
sudo mkdir -p /opt/volunteer-service/frontend

sudo cp backend/target/volunteer-service-backend-0.0.1-SNAPSHOT.jar \
  /opt/volunteer-service/backend/volunteer-service-backend.jar

sudo cp backend/.env /opt/volunteer-service/backend/.env
sudo cp -r frontend/dist/* /opt/volunteer-service/frontend/
```

设置运行用户：

```bash
sudo useradd --system --home /opt/volunteer-service --shell /usr/sbin/nologin volunteer || true
sudo chown -R volunteer:volunteer /opt/volunteer-service/backend
sudo chown -R www-data:www-data /opt/volunteer-service/frontend
```

安装 systemd 服务：

```bash
sudo cp deploy/volunteer-service-backend.service.example \
  /etc/systemd/system/volunteer-service-backend.service

sudo systemctl daemon-reload
sudo systemctl enable volunteer-service-backend
sudo systemctl start volunteer-service-backend
```

检查状态：

```bash
sudo systemctl status volunteer-service-backend
journalctl -u volunteer-service-backend -n 100 --no-pager
```

### 8.4 Nginx 配置

参考：

```text
deploy/nginx.example.conf
```

部署时需要替换：

- `server_name`
- 前端 `root` 目录
- HTTPS 证书路径
- 后端 upstream 地址

常用命令：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Nginx 需要代理：

- `/api/` 到后端 `http://127.0.0.1:8080`
- `/ws/` 到后端 `http://127.0.0.1:8080`，并保留 `Upgrade` 和 `Connection` 头
- 其他路径由前端静态目录处理，并回退到 `index.html`

## 10. 文件上传运维

本地开发默认：

```text

```

## 11. 外部通知运维

### 11.1 邮件

启用真实 SMTP：

```env
VMS_EMAIL_ENABLED=true
VMS_EMAIL_HOST=smtp.example.com
VMS_EMAIL_PORT=465
VMS_EMAIL_USERNAME=your_email_account
VMS_EMAIL_PASSWORD=your_email_authorization_code
VMS_EMAIL_FROM=your_email_account@example.com
VMS_EMAIL_FROM_NAME=志愿者服务管理系统
VMS_EMAIL_AUTH=true
VMS_EMAIL_SSL_ENABLED=true
VMS_EMAIL_STARTTLS_ENABLED=false
```

常见端口：

| 端口 | 配置 |
| --- | --- |
| `465` | `VMS_EMAIL_SSL_ENABLED=true`，`VMS_EMAIL_STARTTLS_ENABLED=false` |
| `587` | `VMS_EMAIL_SSL_ENABLED=false`，`VMS_EMAIL_STARTTLS_ENABLED=true` |

当前系统复用用户 `username` 作为邮件收件地址。需要真实发送邮件时，接收用户必须使用邮箱格式用户名。

### 11.2 短信

短信通道当前为本地发送实现，用于形成外部通知任务、失败记录和重试闭环。若后续接入真实短信服务商，应新增 `ExternalNotificationSender` 适配实现，不应在控制器中直接调用第三方 SDK。

## 12. 安全加固

### 12.1 必做项

- 生产环境使用 HTTPS。
- `VMS_JWT_SECRET` 使用随机强密钥。
- MySQL 不允许公网裸露。
- `backend/.env`、`frontend/.env` 不提交、不放入 Web 目录。
- `VMS_BOOTSTRAP_ENABLED=false`。
- 生产环境不导入 `demo-data.sql`。
- Nginx 增加 HSTS、`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`。
- CORS 白名单只配置真实前端域名。

### 12.2 权限建议

- 后端 systemd 使用独立低权限用户运行。
- 上传目录只给后端运行用户写权限。
- 前端静态目录只给 Nginx 用户读取权限。
- 数据库用户只授予当前库必要权限。

示例：

```sql
CREATE USER 'volunteer_app'@'127.0.0.1' IDENTIFIED BY 'strong_password';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, INDEX, ALTER ON volunteer_service.* TO 'volunteer_app'@'127.0.0.1';
FLUSH PRIVILEGES;
```

## 14. 回滚流程

回滚前准备：

- 保留上一版后端 Jar。
- 保留上一版前端 `dist`。
- 发布前完成数据库备份。

后端回滚：

```bash
sudo systemctl stop volunteer-service-backend
sudo cp /opt/volunteer-service/releases/previous/volunteer-service-backend.jar \
  /opt/volunteer-service/backend/volunteer-service-backend.jar
sudo systemctl start volunteer-service-backend
```

前端回滚：

```bash
sudo rm -rf /opt/volunteer-service/frontend/*
sudo cp -r /opt/volunteer-service/releases/previous/frontend-dist/* \
  /opt/volunteer-service/frontend/
sudo systemctl reload nginx
```

数据库回滚：

- 若本次发布没有执行结构变更，通常只需回滚应用。
- 若执行了结构变更，应先评估是否需要恢复发布前备份。
- 当前项目轻量迁移器不提供自动回滚 SQL，恢复前必须确认业务数据影响。

## 15. 常见故障处理

### 15.1 后端启动失败

检查：

```bash
journalctl -u volunteer-service-backend -n 200 --no-pager
```

常见原因：

- JDK 版本不是 17。
- `backend/.env` 路径错误。
- 数据库密码错误。
- MySQL 未启动。
- 上传目录没有写权限。

### 15.2 数据库连接失败

检查：

```bash
mysql -h 127.0.0.1 -P 3306 -u root -p -e "SELECT 1;"
```

处理：

- 确认 `SPRING_DATASOURCE_URL` 的 host、port、database 正确。
- 确认 MySQL 用户有当前库权限。
- 确认连接串包含 `serverTimezone=Asia/Shanghai` 和 `characterEncoding=UTF-8`。

### 15.3 前端页面 404

通常是 Nginx 没有回退到 `index.html`。

检查 Nginx 配置：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

### 15.4 API 404 或 502

检查：

- 后端是否监听 `8080`。
- Nginx `proxy_pass` 是否为 `http://127.0.0.1:8080`。
- 后端服务是否正在运行。

```bash
curl http://127.0.0.1:8080/api/health
sudo tail -n 100 /var/log/nginx/error.log
```

### 15.5 WebSocket 连接失败

检查 Nginx `/ws/` 配置是否包含：

```nginx
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "Upgrade";
proxy_read_timeout 3600s;
```

同时确认前端访问协议：

- HTTP 页面使用 `ws://`
- HTTPS 页面使用 `wss://`

### 15.6 邮件发送失败

检查：

- `VMS_EMAIL_ENABLED=true`
- SMTP host、port、账号、授权码正确
- SSL 和 STARTTLS 配置与端口匹配
- 接收用户的 `username` 是邮箱格式

管理员可在外部通知任务页面查看失败原因并重试。

### 15.7 文件上传失败

检查：

- 文件类型是否允许。
- 文件大小是否超过限制。
- `VMS_FILE_STORAGE_DIR` 是否存在。
- 后端运行用户是否有写权限。

### 15.8 样例账号无法登录

处理：

1. 确认已执行 `SOURCE backend/src/main/resources/sql/demo-data.sql;`。
2. 确认登录用户名为邮箱格式，例如 `admin@example.com`。
3. 确认数据库中用户状态为 `ENABLED`。

查询：

```sql
SELECT username, account_status, role FROM users WHERE username LIKE '%@example.com';
```

## 16. 日常维护建议

- 每次发布前备份数据库和上传目录。
- 每次发布后执行健康检查和核心页面走查。
- 定期查看 `audit_logs` 中的异常操作。
- 定期清理无效外部通知失败任务，但保留近期故障排查数据。
- 生产环境不要长期使用 root 数据库账号。
- 样例数据和真实数据不要混用。
- 若项目继续长期维护，建议引入 Flyway 或 Liquibase，并重新建立自动化测试体系。
