# 接口文档

本文档用于说明当前项目可运行版本的接口边界、通信方式和外部服务接入方式。文档以当前 `v4` 代码实现为准，不描述尚未落地的独立移动端、真实短信网关、真实支付网关和第三方对象存储联调细节。

## 1. 总体接口原则

系统采用前后端分离架构。前端通过 Vue 3 页面调用后端 Spring Boot REST 接口，后端通过 MySQL、WebSocket、文件存储、SMTP 邮件适配器、模拟短信通道和模拟支付网关支撑业务运行。

接口设计遵循以下原则：

- 业务接口统一使用 `/api` 前缀。
- 除登录、注册、健康检查外，业务接口均需携带 `Authorization: Bearer <token>`。
- 普通业务响应统一使用 JSON 结构，文件下载和 CSV 导出返回二进制流。
- 外部邮件、短信、支付和文件物理存储通过适配端口隔离，业务层不直接绑定具体厂商。
- 外部通知发送失败不影响站内通知落库，失败原因记录在外部通知任务表中。
- 敏感操作需要角色校验和审计留痕。

## 2. 统一响应结构

普通接口响应结构如下：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

说明：

- `code` 表示业务处理结果。
- `message` 表示处理提示或错误原因。
- `data` 表示返回数据。
- 文件下载接口、统计导出接口、审计导出接口不使用该 JSON 结构。

## 4. 文件传输接口

### 4.1 文件上传

- 接口路径：`POST /api/files/upload`
- 请求类型：`multipart/form-data`
- 必填参数：`file`、`category`
- 可选参数：`businessType`、`businessId`
- 当前分类：`IMAGE`、`ATTACHMENT`

文件限制：

- 图片仅允许 `jpg`、`jpeg`、`png`、`gif`，默认最大 5MB。
- 附件仅允许 `pdf`、`docx`、`xlsx`、`pptx`、`zip`、`rar`，默认最大 50MB。
- 后端会读取文件头进行真实类型校验，不只依赖后缀名。
- 上传成功后写入 `file_assets` 审计记录，记录原始文件名、存储名称、大小、上传人、客户端 IP、业务关联对象等信息。

### 4.2 文件下载

- 接口路径：`GET /api/files/{fileId}`
- 返回类型：二进制文件流
- 访问控制：管理员和上传者可访问；公开内容、活动附件可访问；服务记录证明材料仅允许相关用户或管理员访问。

当前文件物理存储通过 `FileObjectStorage` 适配端口隔离，默认实现为本地磁盘 `LocalFileObjectStorage`。后续如需接入 MinIO、阿里云 OSS 或腾讯云 COS，只需替换该适配实现。

## 5. 通知通信接口

### 5.1 站内通知

站内通知以数据库记录为准。系统生成通知时，先写入 `notifications` 表，再尝试通过 WebSocket 推送给在线用户。

- 通知列表：`GET /api/notifications/my`
- 标记已读：`PATCH /api/notifications/{id}/read`
- 实时推送：`/ws/notifications?token=<JWT>`

WebSocket 推送失败不会影响通知记录保存。

### 5.2 外部通知

外部通知任务记录在 `external_notification_tasks` 表中，包含渠道、接收人、标题、内容、发送状态、失败原因、重试次数等字段。

- 外部任务列表：`GET /api/notifications/external-tasks`
- 单条任务重试：`POST /api/notifications/external-tasks/{taskId}/retry`
- 批量重试失败任务：`POST /api/notifications/external-tasks/retry-failed`

外部通知通过 `ExternalNotificationSender` 适配端口发送：

- 邮件通道：可配置 `SmtpEmailNotificationSender` 使用真实 SMTP 发送。
- 短信通道：当前保留 `SimulatedExternalNotificationSender` 模拟发送。

真实邮件启用方式见 `backend/.env.example` 中 `VMS_EMAIL_*` 配置项。默认 `VMS_EMAIL_ENABLED=false`，不配置时 EMAIL/SMS 均使用模拟发送。

当前系统复用用户 `username` 作为邮件收件地址；需要真实发送邮件时，接收用户应使用邮箱格式用户名注册。

## 6. 捐赠支付接口

当前项目实现可演示的捐赠订单和模拟支付闭环。

- 创建捐赠订单：`POST /api/donations/orders`
- 模拟支付回调：`POST /api/donations/orders/{orderId}/simulate-payment`
- 我的订单：`GET /api/donations/orders/my`
- 我的捐赠记录：`GET /api/donations/my`
- 管理员查询全部捐赠：`GET /api/donations`

支付规则：

- 创建订单后状态为 `PENDING`。
- 模拟支付只能将订单更新为 `PAID`、`FAILED` 或 `CANCELLED`。
- 支付回调必须携带订单 `callbackToken`。
- 只有支付成功后才生成正式 `donations` 捐赠记录。

支付 token 生成和回调校验通过 `DonationPaymentGateway` 适配端口隔离，当前默认实现为 `SimulatedDonationPaymentGateway`。后续接入真实支付平台时，应新增真实网关实现并保留现有业务控制器流程。

## 7. 数据库接口

系统使用 MySQL 8，后端通过 Spring Data JPA 和 JDBC 访问数据库。

数据库治理规则：

- 字符集使用 `utf8mb4`。
- 时间区使用 `Asia/Shanghai`。
- 表结构以 `backend/src/main/resources/sql/init.sql` 和 `backend/src/main/resources/sql/migrations/` 为准。
- 启动时由轻量迁移器登记 `schema_migrations` 历史并按兼容判定执行缺失迁移。
- 演示和测试数据统一由 `backend/src/main/resources/sql/demo-data.sql` 维护，需要时通过 MySQL `SOURCE` 命令导入。
- 当前未强制切换 Flyway/Liquibase；如长期维护，可在后续迭代制定 baseline 后迁移。

## 8. 部署与安全接口

部署接口包括健康检查、Nginx 反向代理、安全响应头和 systemd 服务管理。

- 健康检查：`GET /api/health`
- Nginx 示例：`deploy/nginx.example.conf`
- systemd 示例：`deploy/volunteer-service-backend.service.example`
- Ubuntu 配置脚本：`scripts/setup-ubuntu.sh`
- Windows 配置脚本：`scripts/setup-windows.ps1`

安全策略：

- 生产环境建议使用 HTTPS。
- Nginx 示例包含 HSTS、`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`。
- 后端 `SecurityHeadersFilter` 会为 API 响应补充基础安全响应头。
- CORS 白名单通过 `VMS_CORS_ALLOWED_ORIGIN_PATTERNS`、`VMS_CORS_ALLOWED_METHODS`、`VMS_CORS_ALLOWED_HEADERS` 配置。

## 9. 异常处理与审计

后端统一处理认证失败、权限不足、业务规则错误和未处理异常，避免将堆栈信息直接暴露给前端。

关键操作会写入审计日志，包括：

- 用户注册、登录、登出。
- 用户角色、账号状态、实名审核变更。
- 活动创建、编辑、状态变更、报名审核、签到签退和考勤更正。
- 服务记录登记和服务记录更正审核。
- 文件上传。
- 捐赠订单创建和模拟支付。
- 系统配置和故障处理记录。
